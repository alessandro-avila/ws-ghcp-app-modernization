# Route Inventory — ContosoUniversity

_Extracted on 2026-05-13 from `src/ContosoUniversity/`._

## Routing Model

The application uses **only convention-based ASP.NET MVC routing**. There is no attribute routing (no `[Route]`, no `[RoutePrefix]`), no Web API (`ApiController`), no minimal-API surface, and no Areas (although `AreaRegistration.RegisterAllAreas()` is called, no `Area`-derived classes exist in the project).

The single route table entry is registered in [src/ContosoUniversity/App_Start/RouteConfig.cs](src/ContosoUniversity/App_Start/RouteConfig.cs):

```csharp
routes.IgnoreRoute("{resource}.axd/{*pathInfo}");
routes.MapRoute(
    name: "Default",
    url: "{controller}/{action}/{id}",
    defaults: new { controller = "Home", action = "Index", id = UrlParameter.Optional }
);
```

This produces URLs of the shape `/{Controller}/{Action}/{id?}`. The application's root URL (`/`) resolves to `HomeController.Index`. The `{id}` route token is bound to the action's first `int? id` (or `int id`) parameter when present; otherwise it is ignored.

Per [src/ContosoUniversity/App_Start/FilterConfig.cs](src/ContosoUniversity/App_Start/FilterConfig.cs), the only global filter is `HandleErrorAttribute`. **No `[Authorize]` attribute is applied to any controller or action, no global authorization filter is registered, and no role checks exist in any action body.** A comment in `FilterConfig.cs` reads *"Remove the global authorization filter since we're implementing role-based authorization"*; in code, that role-based authorization is not present.

`Web.config` enables Windows authentication for IIS Express (`<system.webServer><security><authentication><windowsAuthentication enabled="true" />`), but the application code does not consume `User.Identity` for authorization. The only place `User.Identity.Name` is read is `MessageQueueTestController.SendTestNotification` (falls back to `"TestUser"`). All notifications generated by the rest of the controllers are tagged with the hard-coded user name `"System"` (see `BaseController.SendEntityNotification`).

## Conventions Observed

- **Action method naming**: GET endpoints have no `[HttpGet]` attribute; POST endpoints carry `[HttpPost]` plus `[ValidateAntiForgeryToken]` (except `NotificationsController.MarkAsRead` and all 4 `MessageQueueTestController` POSTs, which lack `[ValidateAntiForgeryToken]`).
- **Bind allow-listing**: All POST mutators that accept entities use `[Bind(Include = "...")]` to restrict mass-assignment.
- **Delete pattern**: Every CRUD-bearing controller uses the GET `Delete/{id}` → POST `Delete/{id}` → action method `DeleteConfirmed` (rewritten as `Delete` via `[ActionName("Delete")]`) idiom.
- **Anti-forgery token**: Applied to all mutator POSTs in `Students/Courses/Instructors/Departments`. **Not** applied to `NotificationsController.MarkAsRead` or any `MessageQueueTestController` POST.
- **Synchronous EF Core**: Every action calls EF Core with `Find`, `Single`, `ToList`, `SaveChanges` — no `async`/`await`.
- **Notification publishing**: After every successful `db.SaveChanges()`, controllers in `Students/Courses/Instructors/Departments` invoke `BaseController.SendEntityNotification(entityType, entityId, [displayName,] EntityOperation.{CREATE|UPDATE|DELETE})`. Failures inside `SendEntityNotification` are swallowed and written to `Debug.WriteLine`.
- **Comments vs code**: Several inline comments in `StudentsController` and `InstructorsController` claim role-based behavior such as `// GET: Students - Admins and Teachers can view` or `// POST: Instructors/Delete/5 - Only admins can delete instructors`. These comments are **not** enforced by any attribute or code path; the actions are reachable by any HTTP caller.

## Documentation vs Code

- `Web.config` configures `<authentication mode="None" />` in `<system.web>` — i.e., ASP.NET-level authentication is disabled. IIS-level Windows authentication is enabled in `<system.webServer>`. The application code does not perform any role-based authorization despite contradictory inline comments and `FilterConfig.cs` commentary.
- The `csproj` declares `<Reference Include="System.Messaging" />` and `Web.config` has `<add key="NotificationQueuePath" value=".\Private$\ContosoUniversityNotifications" />` — these strings imply MSMQ. At runtime, the `NotificationsController` and other consumers route through `Infrastructure.MessageQueue` (in-memory). Notifications do not survive an `AppDomain` recycle.
- `MessageQueueTestController` is registered with the default route, exposing 5 endpoints under `/MessageQueueTest/...` to any anonymous caller.
- `Examples/MessageQueueExample.cs` is included in `<Compile>` but is not exposed as a controller and has no MVC route.
